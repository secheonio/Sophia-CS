# 최종 검증 체크리스트

본 문서는 현재까지 구현된 지출품의 결재 시스템의 최종 완성도를 높이기 위해, 실제 브라우저 기준으로 순서대로 점검할 수 있도록 정리한 체크리스트입니다.

아래 항목은 번호 순서대로 실행하는 것을 원칙으로 하며, 각 항목을 완료하면 해당 체크박스를 `[x]`로 바꿔서 진행 상태를 관리합니다.

---

# 1. 관리자 예산표 관리 기능 설계안

## 1-1. 목표
관리자가 예산표를 직접 관리할 수 있도록 하여, 하드코딩된 예산표가 아니라 DB 기반 마스터 데이터로 운영되게 만드는 것이 핵심 목표입니다.

- 상신 단위별 예산표를 DB에서 관리
- 요청서 작성 시 해당 단위의 예산표를 불러와 사용
- 관리자(교장)가 예산표를 수정·추가·삭제 가능
- 실제 지출품의 작성 흐름과 결재 흐름에 연결
- 정해진 10개 상신 단위 기준으로 고정 운영

## 1-2. 관리 대상 상신 단위
다음 10개 상신 단위는 마스터 예산표의 기본 단위로 사용합니다.

1. 기초과정
2. 본과정
3. 심화과정
4. 교무부
5. 교육과정연구부
6. 생활교육부
7. 전형위원회
8. 델포이
9. 생활관
10. 행정실

## 1-3. DB 설계안
예산표는 `budget_master` 테이블을 기본으로 관리하는 구조를 권장합니다.

```sql
CREATE TABLE budget_master (
  department TEXT PRIMARY KEY,
  rows_json TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

### 의미
- `department`: 상신 단위명
- `rows_json`: 해당 부서의 예산 행 목록을 JSON 문자열로 저장
- `updated_at`: 마지막 수정 시각

### 예산 행 구조 예시
```json
[
  {
    "관": "교육활동비",
    "항": "교과 및 재량비",
    "목": "교재 및 교구비",
    "세목": "교구비",
    "내역": "기초과정 실습 교구",
    "예산총액": 5000000,
    "예산잔액": 5000000,
    "집행률": 0
  }
]
```

## 1-3A. 예산 사용량·집행률 저장 설계안 (권장)
요구사항상 가장 중요한 것은 “예산 총액, 예산 잔액, 집행률”을 기안 작성 시 참고하고, 품의 완료 후 잔액을 차감하여 다시 계산하는 구조입니다. 단순히 JSON 안에 `예산잔액`과 `집행률`을 덮어쓰는 방식은 추적성이 약하고, 승인/반려/수정 이력이 누락되기 쉽습니다.

따라서 추천 구조는 다음 2단계로 나누는 것입니다.

### A. 마스터 예산 행
```sql
CREATE TABLE budget_rows (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  department TEXT NOT NULL,
  gwan TEXT NOT NULL,
  hang TEXT NOT NULL,
  mok TEXT NOT NULL,
  semok TEXT NOT NULL,
  nae TEXT NOT NULL,
  total_amount INTEGER NOT NULL,
  remaining_amount INTEGER NOT NULL,
  execution_rate REAL NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL,
  UNIQUE (department, gwan, hang, mok, semok, nae)
);
```

- `total_amount`: 예산 총액
- `remaining_amount`: 현재 남은 예산
- `execution_rate`: 계산식 기반의 집행률
- `updated_at`: 마지막 갱신 일시

### B. 품의별 예산 사용 기록
```sql
CREATE TABLE request_budget_allocations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id INTEGER NOT NULL,
  budget_row_id INTEGER NOT NULL,
  requested_amount INTEGER NOT NULL,
  approved_amount INTEGER NOT NULL DEFAULT 0,
  allocated_at TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',
  FOREIGN KEY (request_id) REFERENCES requests(id),
  FOREIGN KEY (budget_row_id) REFERENCES budget_rows(id)
);
```

- `requested_amount`: 사용자가 기안에서 설정한 예산액
- `approved_amount`: 최종 승인된 금액
- `status`: pending / approved / rejected / paid

## 1-3B. 계산 규칙
기안 작성 시에는 다음을 수행합니다.

1. `budget_rows.remaining_amount`를 읽어 현재 잔액 확인
2. 사용자가 입력한 예산액이 잔액보다 크면 기안 불가
3. 승인 전에 `request_budget_allocations`에 임시 예약 기록 가능
4. 최종 승인 후 `approved_amount`를 반영
5. 잔액은 다음 공식으로 갱신

```text
new_remaining = previous_remaining - approved_amount
```

6. 집행률은 다음 공식으로 계산

```text
execution_rate = ((total_amount - remaining_amount) / total_amount) * 100
```

예시:
- 총액: 5,000,000
- 잔액: 3,200,000
- 사용액: 1,800,000
- 집행률: ((5,000,000 - 3,200,000) / 5,000,000) * 100 = 36%

## 1-3C. 반려/취소 처리 방식
반려되거나 기안이 취소되면 해당 금액을 다시 환원해야 합니다.

```text
remaining_amount = remaining_amount + approved_amount
```

이런 방식으로 통계와 잔액이 항상 일관성을 유지하게 됩니다.

## 1-3D. JSON 방식 유지가 필요한 경우의 대안
현재 구조가 `budget_master` + `rows_json` 방식을 유지하고 싶다면, 최소한 다음 필드를 JSON 내부에 포함해야 합니다.

```json
{
  "관": "교육활동비",
  "항": "교과 및 재량비",
  "목": "교재 및 교구비",
  "세목": "교구비",
  "내역": "기초과정 실습 교구",
  "예산총액": 5000000,
  "예산잔액": 3200000,
  "집행률": 36,
  "사용액": 1800000,
  "updated_at": "2026-10-28"
}
```

이 방식은 빠르게 구현할 수 있지만, 실제 운영에서는 다음 문제가 생깁니다.

- 승인/반려 이력이 남지 않음
- 여러 품의가 같은 행을 공유할 때 충돌 가능성 있음
- 집행률 계산이 중복 계산으로 번질 수 있음
- 추적이 어려움

따라서 운영 수준에서는 `budget_rows` + `request_budget_allocations` 구조가 가장 안전합니다.

## 1-4. 관리자 예산표 관리 UI 설계안
관리자(교장)는 예산표 관리 화면에서 부서별 예산표를 직접 수정하고 저장할 수 있어야 합니다. 여기에는 다음 기능이 포함되어야 합니다.

- 행 추가
- 행 삭제
- 예산 항목 값 수정
- 관·항·목·세목·내역 문자열 수정
- 예산 총액(예산금액) 재조정
- 수정 직후 해당 상신 단위의 예산표에도 즉시 반영

사용자는 이 화면을 통해 실제 예산 행을 보며, 각 행의 총액·잔액·집행률을 검토하고, 필요한 통계 값을 계산할 수 있습니다.

### 1-4-1. 화면 레이아웃
관리자 페이지는 다음 구조가 가장 적합합니다.

- 좌측 사이드바
  - 사용자 관리
  - 예산표 관리
  - 결재 관리
  - 지출 처리

- 메인 영역
  - 상단: 상신 단위 선택 탭
  - 중단: 예산표 그리드
  - 하단: 저장 버튼 + 요약 카드

### 1-4-2. 상신 단위 선택
상단에는 다음 10개 상신 단위 중 하나를 선택하는 탭 또는 드롭다운을 둡니다.

1. 기초과정
2. 본과정
3. 심화과정
4. 교무부
5. 교육과정연구부
6. 생활교육부
7. 전형위원회
8. 델포이
9. 생활관
10. 행정실

선택 시 해당 부서의 예산표를 서버에서 로드해서 화면에 표시합니다.

### 1-4-3. 예산표 그리드
테이블의 열은 다음을 기준으로 구성합니다.

- 관
- 항
- 목
- 세목
- 내역
- 예산총액
- 예산잔액
- 집행률
- 액션(수정/삭제)

관리자는 이 표에서 직접 다음을 조정할 수 있어야 합니다.

- 항목 추가
- 항목 삭제
- 관·항·목·세목·내역 문자열 수정
- 예산 총액(예산금액) 수정
- 저장 시 비워진 값은 허용하지 않음

### 1-4-4. 행 동작
각 행에는 다음 기능이 필요합니다.

- 행 추가: 빈 행을 추가해 새 예산 항목 생성
- 행 수정: 값 편집
- 행 삭제: 해당 항목 제거
- 행 복제: 동일한 항목을 빠르게 복사해서 새 비목 작성

### 1-4-5. 저장 흐름
관리자가 예산표를 수정한 뒤 저장 버튼을 누르면 다음 순서로 처리합니다.

1. 현재 선택된 부서 확인
2. 각 행의 값 정리
3. 각 행에 대해 `total_amount`, `remaining_amount`, `execution_rate` 재계산
4. 서버에 `rows` 배열 전송
5. 서버가 `remaining_amount`와 `execution_rate` 검증 후 DB 저장
6. 해당 상신 단위의 예산표 목록과 현재 품의 양식에서 사용 중인 예산 데이터도 즉시 재동기화
7. 화면에서는 마지막 저장 시각 표시

### 1-4-6. 즉시 반영 규칙
예산표가 수정되면 동일한 상신 단위의 예산표는 즉시 재로드되어야 합니다.

- 관리자 편집 후 저장 시 해당 상신 단위의 표가 즉시 갱신
- 새로 기안할 때 수정된 금액이 반영됨
- 이미 열려 있는 품의 작성 화면에서도 최신 값이 다시 로드되도록 재동기화
- 사용자가 선택한 예산 행의 총액과 잔액이 새 기준으로 반영됨

### 1-4-7. 예산 총액 재조정 로직
예산 총액은 항목별 단위의 총액만 바꾸는 것이 아니라, 각 상신 단위의 전체 예산표를 기준으로 재계산해야 합니다.

- 각 예산 행은 고유 `total_amount`를 가짐
- 상신 단위 전체는 이 값들의 합계로 요약
- 관리자 수정 후 저장 시 상신 단위의 총 예산 합계 자동 재계산
- 예산 잔액은 다음 규칙을 따라 계산

```text
remaining_amount = total_amount - already_used_amount
```

여기서 `already_used_amount`는 승인된 품의 금액 합계이며, 실제로는 `request_budget_allocations`의 승인 금액 총합을 기준으로 계산합니다.

### 1-4-8. 반려/취소 연동
예산액 변경과 품의 결재 상태는 연결됩니다.

- 품의 승인 시 해당 행의 사용 금액이 반영됨
- 반려 시 사용 금액이 되돌아감
- 예산표 수정 후에도 이미 승인된 품의는 기존 결재 기준으로 이어질 수 있도록 별도 로그를 유지
- 신규 기안은 최신 예산 잔액 기준으로 판단

### 1-4-6. 계산 UI
예산표 하단에는 다음 요약 정보가 보이도록 합니다.

- 총 예산
- 현재 잔액 합계
- 집행률 평균
- 사용 금액 합계

이 요약 정보는 서버에서 계산해 준 값 또는 클라이언트에서 재계산해 보여주되, 최종 기준값은 서버 계산을 신뢰하는 구조가 안전합니다.

### 1-4-7. 예외 처리
다음 상황은 반드시 처리해야 합니다.

- 예산액이 음수인 경우 차단
- 잔액이 총액을 초과하는 경우 차단
- 집행률이 0~100 범위를 벗어나지 않도록 제한
- 행 이름이 비어 있으면 저장 불가
- 삭제 시 다른 품의에서 사용 중인 예산 행을 참조하고 있다면 경고 표시

## 1-5. API 설계안
다음 API를 추가해 운영 흐름을 정리하는 것을 권장합니다.

### 예산표 조회
- `GET /api/budget-master`
- 관리자 또는 로그인 사용자가 접근 가능
- 전체 10개 부서의 예산표를 반환

### 단일 부서 예산표 조회
- `GET /api/budget-master/:department`
- 특정 상신 단위의 예산표를 반환

### 예산표 저장
- `POST /api/budget-master/:department`
- 관리자 인증 필요
- JSON으로 `rows` 배열을 받음
- 행 추가/삭제/수정 전부 반영
- `total_amount`, `remaining_amount`, `execution_rate` 재계산 후 저장
- 저장 직후 해당 상신 단위 예산표 전체를 다시 갱신

### 예산표 삭제/초기화
- `DELETE /api/budget-master/:department`
- 필요 시 기본값으로 재초기화

### 실사용량 조회
- `GET /api/budget-master/:department/usage`
- 해당 부서에서 사용 중인 품의 금액 합계, 승인 금액 합계, 잔액 요약 반환

### 관리자 예산표 변경 이벤트
- `POST /api/budget-master/:department/reload`
- 저장 직후 클라이언트에 예산표 변경 이벤트를 브로드캐스트하거나, 다음 조회 시 즉시 갱신
- 브라우저 상태와 서버 상태가 같은 시점에 맞추어 동기화

## 1-6. 관리자 기능 요구사항
관리자(교장)는 예산표 관리 화면에서 다음 작업을 수행할 수 있어야 합니다.

- 부서별 예산표 목록 조회
- 예산표 행 추가
- 예산표 행 수정
- 예산표 행 삭제
- 예산 총액, 잔액, 집행률 계산 확인
- 예산표 저장 시 자동 시간 반영
- 변경 사항을 실제 요청서에서 즉시 반영
- 반려 또는 취소된 품의 금액이 잔액에 다시 반영되는지 확인
- 관리자 수정사항이 해당 상신 단위의 예산표에 즉시 반영되는지 확인

## 1-7. 요청서 연동 방식
품의 작성 화면에서는 다음 흐름으로 동작해야 합니다.

1. 상신 단위를 선택
2. 서버에서 해당 부서의 예산표를 조회
3. 예산 테이블에서 행 선택
4. 선택된 행의 값이 다음 항목에 자동 반영
   - 관
   - 항
   - 목
   - 세목
   - 내역
5. 사용자가 기안 금액 입력
6. 서버가 해당 행의 현재 `remaining_amount`와 비교하여 사용가능 금액을 확인
7. 승인 시 `request_budget_allocations`에 기록
8. 지출 완료 상태가 되면 잔액이 실제 차감
9. 반려 시 원복 처리

## 1-8. 운영 규칙

- 요청서 작성 화면은 읽기 전용 데이터로만 사용
- 예산표 변경은 저장 후 즉시 반영
- 각 상신 단위는 고정 이름을 유지하여 데이터 불일치 방지
- 예산 사용 금액은 승인 기준으로만 잔액 차감

- 집행률은 계산식 기반으로 재산출되어야 하며, 임의 값 저장을 금지함

# 2. 실제 브라우저 기준 최종 검증 체크리스트

아래는 브라우저에서 실사용 흐름을 기준으로 순차적으로 확인하는 최종 체크리스트입니다. 각 항목을 순서대로 수행하고, 완료 시 체크 표시를 남기세요.

## [ ] 1. 로컬 서버 및 프론트엔드 정상 구동 확인
- 브라우저 주소가 `http://127.0.0.1:3100/` 인지 확인
- 서버가 정상 실행 중인지 확인
- 로그인 화면이 정상 표시되는지 확인
- 브라우저 콘솔에 오류가 없는지 확인

검증 포인트:
- 페이지가 열리면서 로딩이 멈추지 않는지
- 백엔드와 프론트엔드가 같은 포트/경로 기준으로 연결되는지

## [ ] 2. 관리자 로그인 확인
- 교장 계정으로 로그인
  - 예: `박세천 / gyver0979`
- 세션 유지 여부 확인
- 로그인 후 관리자 메뉴 진입 가능 여부 확인

검증 포인트:
- 교장 계정만 관리자 메뉴를 확인할 수 있는지
- 로그인 실패 시 메시지가 적절한지

## [ ] 3. 사용자 관리 화면 접근 확인
- 사용자 관리 탭 진입 가능 여부 확인
- 사용자 목록이 정상 표시되는지 확인
- 사용자 추가, 수정, 삭제 버튼 동작 여부 확인
- 다중 소속/직책 정보가 올바르게 표시되는지 확인

검증 포인트:
- 교장이 아닌 계정은 사용자 관리 화면 진입이 제한되는지
- 사용자 목록과 실 DB 값이 일치하는지

## [ ] 4. 사용자 정보 수정 저장 흐름 확인
- 사용자의 부서/직책/상태 수정 후 저장
- 저장 버튼 클릭 후 변경 값이 실제로 반영되는지 확인
- 페이지 새로고침 후에도 값 유지 여부 확인

검증 포인트:
- 수정 후 서버 반영이 즉시 되며, 저장 전/후 값 차이가 명확한지
- 저장 실패 시 경고 메시지가 노출되는지

## [ ] 5. 임시 비밀번호 및 비밀번호 초기화 정책 확인
- 신규 계정 생성 시 임시 비밀번호 정책 확인
- 비밀번호 초기화 시 임시 비밀번호 값이 `sophia00`인지 확인
- 첫 로그인 시 비밀번호 변경 화면으로 이동하는지 확인

검증 포인트:
- 임시 비밀번호 값이 일관되게 유지되는지
- 기존 값과 불일치가 없는지

## [ ] 6. 이메일·전화번호 검증 규칙 확인
- 정상 이메일 예시 확인
  - `namisuk@school.local`
  - `moonsookyoung@school.local`
  - `anstnrdud@naver.com`
- 비정상 형식 입력 시 에러 메시지가 표시되는지 확인
- 전화번호 필드 형식이 `000-0000-0000` 형식 기준으로 통과/거절되는지 확인

검증 포인트:
- 서버와 브라우저 검증 규칙이 일치하는지
- 이메일 문자열이 `@` 포함 여부만으로 통과되는지 여부가 요구사항과 일치하는지

## [ ] 7. 비밀번호 변경 및 내정보수정 흐름 확인
- 로그인 후 내정보수정 또는 비밀번호 변경 화면 진입
- 이메일/전화번호 값 수정 가능 여부 확인
- 비밀번호 변경 시 현재 비밀번호 확인이 필요한지 확인
- 변경 후 세션이 정상 재발급 또는 재로그인 흐름이 되는지 확인

검증 포인트:
- 비밀번호를 변경하지 않고도 연락처만 수정 가능한지
- 비밀번호 변경 시 규칙이 서버와 UI에서 일관되는지

## [ ] 8. 상신 단위 버튼 동작 확인
- 각 상신 단위 버튼 클릭 시 새 품의 작성 화면이 열리는지 확인
- 선택한 상신 단위가 자동으로 기본 부서로 들어가는지 확인
- 해당 부서의 결재선 미리보기가 나타나는지 확인

검증 포인트:
- 10개 상신 단위가 모두 정상 동작하는지
- 기안 대상 부서와 실제 결재선이 일치하는지

## [ ] 9. 예산표 선택 및 자동 채우기 확인
- 상신 단위를 선택한 뒤 예산표 목록이 표시되는지 확인
- 예산 행 선택 시 다음 필드가 자동으로 채워지는지 확인
  - 관
  - 항
  - 목
  - 세목
  - 내역
- 금액과 사용 목적 입력까지 정상 작동하는지 확인

검증 포인트:
- 선택한 행의 값이 폼에 정확히 반영되는지
- 예산표 값이 비어 있지 않은지

## [ ] 10. 관리자 예산표 관리 화면 확인
- 관리자 메뉴에서 예산표 관리 진입
- 부서별 탭/목록 표시 여부 확인
- 예산 행 추가 버튼 동작 확인
- 수정 후 저장 시 반영 여부 확인
- 새로고침 후에도 저장 결과 유지 여부 확인

검증 포인트:
- 예산표 관리 화면이 실제로 DB 기준으로 동작하는지
- 부서별 표가 별도로 저장되는지

## [ ] 11. 관리자 예산표 저장 후 요청서 반영 확인
- 관리자에서 특정 부서의 예산표 행 변경
- 해당 부서로 새 품의 작성
- 변경된 예산표가 요청서에서 그대로 보이는지 확인

검증 포인트:
- 하드코딩 값이 아니라 서버 저장 값이 사용되는지
- 새로고침 후에도 반영되는지

## [ ] 12. 결재선 생성 규칙 확인
- 품의 생성 후 결재선이 다음 형태로 구성되는지 확인
  - 소속장 결재
  - 행정실장(교장 결재 대기중)
  - 교장 결재
- 결재 단계 순서가 실제 UI와 서버 규칙과 일치하는지 확인

검증 포인트:
- 결재 단계 이름이 일치하는지
- 주문 순서가 요구사항대로 동작하는지

## [ ] 13. 결재 승인 및 반려 흐름 확인
- 결재자 계정으로 로그인
- 승인 버튼 클릭 시 상태가 변경되는지 확인
- 반려 사유 입력 후 반려 처리 확인
- 반려된 품의가 수정 후 재상신되는지 확인

검증 포인트:
- 승인/반려 상태가 일관되게 전환되는지
- 반려 사유가 남는지

## [ ] 14. 지출 처리 흐름 확인
- 교장 결재 이후 행정실장 지출 처리 단계가 정상 활성화되는지 확인
- 지출 완료 상태가 표시되는지 확인
- 지출 완료 금액 합계가 UI에서 정상 반영되는지 확인

검증 포인트:
- 결재 완료 후 지출 대기/지출 완료 상태 전환이 올바른지
- 마지막 단계의 라벨과 상태가 일치하는지

## [ ] 15. 첨부파일 및 상세 정보 확인
- 품의 첨부파일 업로드가 정상되는지 확인
- 파일 용량 제한 및 확장자 제한이 적용되는지 확인
- 품의 상세 페이지에서 금액, 목적, 항목, 결재 단계가 정상 표시되는지 확인

검증 포인트:
- 이미지 파일 업로드가 허용되는지
- 비정상 파일이 차단되는지

## [ ] 16. 목록/검색/필터 동작 확인
- 품의 목록 필터가 작동하는지 확인
- 상태별 탭이 정상 동작하는지 확인
- 검색창에서 기안자/제목/부서 검색이 되는지 확인
- 정렬 및 선택 상태가 정상 유지되는지 확인

검증 포인트:

## [ ] 17. 예외 상황 점검
- 비활성 계정 로그인 방지
- 잘못된 비밀번호 입력 시 동일한 오류 메시지 처리

- 사용자 삭제와 결재 데이터 간 일관성 확인

검증 포인트:
